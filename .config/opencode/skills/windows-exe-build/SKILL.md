# Сборка Windows EXE (production-подход)

Навык для подготовки и (по возможности) сборки исполняемых файлов Windows из текущего окружения. Среда часто **Linux (в т.ч. aarch64), офлайн**, с ограниченным набором toolchain — сначала проверяй факты и выбирай реалистичный путь.

## 1. Факты перед работой

```bash
uname -a; uname -m
node -v; npm -v 2>/dev/null
python3 --version; pip3 --version 2>/dev/null
which gcc g++ make cmake wine x86_64-w64-mingw32-gcc dotnet go rustc cargo 2>/dev/null || true
```

Уточнить тип приложения: консоль/GUI, язык/фреймворк, целевая архитектура (x64/x86/ARM64 Windows), нужны ли инсталлятор, автообновление, подпись.

## 2. Главные ограничения

- **Кросс-компиляция в .exe на Linux офлайн** часто невозможна без нужных SDK/компиляторов/рантаймов (MinGW, .NET SDK, Electron binaries для Windows, PyInstaller bootloader под Windows и т.д.). Нельзя устанавливать недостающие компоненты из интернета в офлайн-среде.
- **Продакшен EXE** обычно требует сборки на целевой платформе или в подготовленном CI (Windows runner) с теми же архитектурой/зависимостями. Если локально собрать нельзя — готовь проект, скрипты сборки и инструкцию воспроизводимой сборки на Windows.
- Не обещать «готовый production exe» без подтверждённой возможности собрать и проверить.

## 3. Выбор стратегии

| Стек/цель | Реалистичный путь в этой среде | Примечание |
|---|---|---|
| Node.js CLI/сервис | Подготовить проект + `npm ci` (если lock и кэш есть) + запуск через `node`; для single-exe рассмотреть **Node SEA** (Single Executable Applications, поддержка зависит от версии Node) | Для Windows-бинарника SEA обычно нужна сборка/инъекция blob на Windows или соответствующие инструменты; проверить `node --experimental-sea-config` |
| Python | Подготовить исходники + `requirements` (оффлайн-колёса если есть), entrypoint; для exe на Windows — **PyInstaller/cx_Freeze/Nuitka** на Windows-машине/CI | PyInstaller не кросс-компилирует «из коробки»; нужен таргет-окружение |
| .NET | Нужен .NET SDK; `dotnet publish -r win-x64 --self-contained` даёт exe на Windows runner/хосте | Если `dotnet` отсутствует — сборка здесь невозможна |
| C/C++ native | MinGW-w64 кросс-компилятор (`x86_64-w64-mingw32-gcc`) или MSVC на Windows | Без toolchain локально не собрать |
| Electron/Tauri/GUI | Требуются платформенные бинарники/зависимости | Обычно сборка/упаковка под Windows делается на Windows или в CI с кэшем |

## 4. Практические сценарии

### 4.1 Node.js — подготовка и (где возможно) single executable
- Проверить версию: Node 22+ поддерживает SEA в развитии; API/флаги зависят от версии.
- Общая идея SEA: конфиг JSON → генерация blob (`node --experimental-sea-config sea-config.json`) → копия node-бинарника → внедрение blob (на Linux через `postject` или платформенные средства; для Windows нужен Windows `node.exe`).
- Если нет инструментов для внедрения/Windows-бинарника офлайн: подготовить `dist/` скрипт, `pkg.json`/конфиги, и инструкцию сборки на Windows:
  - установить Node LTS той же мажорной версии,
  - `npm ci --omit=dev`,
  - выполнить шаги SEA/упаковщика, протестировать.

Пример заготовки `sea-config.json` (адаптировать под проект):
```json
{ "main": "dist/app.js", "output": "sea-prep.blob", "disableExperimentalSEAWarning": true }
```

### 4.2 Python — production-дистрибуция
- Зафиксировать зависимости (`requirements.txt` с версиями), точку входа (`__main__`/CLI), версионирование.
- Для Windows production exe на Windows-хосте (рекомендуемый воспроизводимый путь):
  - создать venv, установить deps из lock/локальных wheel,
  - `pyinstaller --onefile --name app --clean --noconfirm entry.py` (GUI: `--windowed`; добавить иконку/ресурсы/hidden-imports по факту).
  - протестировать на чистой Windows (без Python).
- В офлайн Linux без PyInstaller: можно подготовить `python -m zipapp` архив (`.pyz`) для сред, где есть Python, и документацию по сборке `.exe` на Windows; это **не** нативный Windows exe.

### 4.3 C/C++ (если установлен mingw — проверить)
```bash
x86_64-w64-mingw32-gcc -O2 -static -o app.exe main.c
x86_64-w64-mingw32-g++ -O2 -static -std=c++17 -o app.exe main.cpp
```
Статическая линковка уменьшает зависимость от DLL, но увеличивает размер; тестировать на Windows.

### 4.4 Универсальная подготовка (когда сборка exe здесь невозможна)
1. Привести проект в воспроизводимое состояние: lock-файлы, скрипты `build`/`package`, версия, конфиг.
2. Написать `BUILD_WINDOWS.md`/скрипт: точные команды, версии toolchain, артефакты, где лежит результат.
3. Добавить smoke-тесты/чек-лист запуска на Windows.
4. Если в LAN есть Windows-машина — передать исходники/артефакт сборки через разрешённые локальные каналы (без облаков по умолчанию), собрать и вернуть exe для проверки.

## 5. Production-чеклист для Windows EXE

- [ ] Целевая архитектура (x64/ARM64), версия ОС (Windows 10/11/Server) определены.
- [ ] Версия приложения/файла (`ProductVersion`, `FileVersion`) проставлена.
- [ ] Зависимости собраны/вшиты; работает на «чистой» системе без dev-toolchain.
- [ ] Иконка, манифест (DPI/permissions/asInvoker при необходимости), корректные пути/кодировки.
- [ ] Конфиги/секреты не захардкожены; логи и ошибки информативны.
- [ ] Антивирусные ложные срабатывания учтены (подпись кода снижает риск; signing cert — секрет, требует безопасного хранения).
- [ ] Подпись Authenticode (signtool) — выполнять на доверенной Windows-среде при наличии сертификата.
- [ ] Инсталлятор/portable-формат выбран (MSI/Inno Setup/NSIS/zip), проверены права записи в `%ProgramFiles%`/`%AppData%`.
- [ ] Smoke/регрессионные тесты на целевой Windows выполнены.

## 6. Безопасность и офлайн-правила

- Не скачивать toolchain/бинарники из интернета без явной необходимости и доступности сети; не устанавливать пакеты «вслепую».
- Не встраивать токены, пароли, ключи подписи в репозиторий и exe; keystore/cert хранить отдельно.
- Фиксировать, что реально собрано и где проверено (локально/на Windows), без имитации успешной сборки.
